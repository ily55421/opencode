两个不受预设影响的结论。 CR-1a（含 -c / --ext-diff / -O 的命令不再落盘成通配许可）不占任何运行时开销： 本轮实测里，批准一次 git -c core.fsmonitor=… status 会落盘 git -c *， 等于一次点击换来任意代码执行的永久许可，而审批头显示的文本长得像 status。 CR-8（更正 优势对比清单.md 的三条"无通用断路器"）是账目正确性，与快慢、与安全目标都无关。 无论切到哪套预设，这两项都该先做。

CR-5 与 CR-6 记为「先量」：机制在 crush 侧确认存在，但本仓的危害大小还没测 —— 内联工具输出的 ANSI 走向、 每帧成本是否真的与列表长度相关，都不许直接开工。CR-9 是所有 [转述] 结论的收口，它决定 CR-1b 与 CR-3c 是否成立。

本页唯一的 P0 是 CR-1（拆 1a/1b 两行，合计 1.25 人日）。CR-3a 分数不低，但它是本轮唯一"必须做且要大"的一块。

评分模型

工程判断，不是实测

与 16 项那页、OpenHands 那页同口径：单个维度 1–5 分，加权后 ×20 映射到 100 分；唯一的实测数据是工期估算与证据等级。 这样做的理由是这批收益大多不是"功能有没有"，而是"一次点击会不会变成永久许可、失败时模型和用户能不能自救"。 切换预设，象限、ROI、热力表总分、对比表全部重算。

CR-1 持久许可的 key 不看 flag 先做 · 1.25d（拆 1a/1b）

本轮唯一 P0：一次普通批准换来对整个 flag 维度的永久许可，其中 git -c * 等于任意代码执行。

  • 我方实测（本轮跑出）：shell/parse.ts 的 prefix() + ARITY（git: 2）产出 save: "<前缀> *"；ShellDanger.classify() 对全部下列输入返回 safe，rememberable() 返回 true：git push origin main → git push *、git push --force origin main → git push *、git -c core.fsmonitor=/tmp/evil status → git -c *、docker rm --force x → docker rm *、kubectl delete pod x --grace-period=0 → kubectl delete *。对照组 rm -rf /、curl x | sh 正常升级，证明不是探针误用。
  • 对方机制：tools/safe.go 的 entry{restrictFlags, allowFlags, denyFlags, requireFlag, allowOperands}，加 gitCodeExecFlags（--ext-diff --textconv --open-files-in-pager -O --output --upload-pack --receive-pack --exec），注释原文："a repository the user cloned but does not control chooses what executes"。
  • 边界：只改 save 字符串的形状，不碰 findLast 折叠、不碰事件词汇（C14/C23 已否决）。key 形状要按「flag 集相同即命中」，不要退化成逐字符命令串——对方把 grant 钉到 exact command 的代价是换参数就问。
  • 未证：端到端（批准 → 第二次是否真不问）本轮没跑，它决定 CR-1b 降级还是成立；GrantKey 细节是 [转述]，见 CR-9。
轴：权限证据：本轮实测（本仓探针 + 对方源码）

CR-2 「不问但仍拦」的第四档 规划 · 1.5d

想无人值守但又不想 rm -rf $TARGET 静默执行的人，现在无路可走。

  • 我方实测：composer/permission-mode.ts 的 MODES = ["ask","auto","full"]；ruleset("full") 是单条 {*,*,allow}；doc/permissions.md 写死 "The only thing that clears it is a session that allowed everything outright"。
  • 对方机制：PermissionMode{Normal, Yolo, Sysadmin}，SkipsPrompts() 只管问不问，执行时仍查 resolveBlockedCommands（条件是 mode != Sysadmin）。
  • 前置约束：same() 用 JSON.stringify 逐条比较 ruleset 来反推档位 —— 新档必须带可区分的标记，否则会静默继承 full 的 escalation 豁免。
  • 禁止照搬：对方把 Sysadmin 放进 Shift+Tab 盲按环（code → plan → YOLO → sysadmin → code），四次按键里含一个"什么都不检查"的档位。借两轴，不借键位。
轴：权限证据：本轮实测（双方）

CR-3 LSP 运行时（a 战略 / b 规划 / c 条件） 7.5d 整块

本轮唯一新方向：配置面与 UI 面都已就位，只有运行时缺席 —— 半条腿，不是没想过。

  • 我方实测：schema/config/lsp.ts 定义 ConfigLSP.Server/Entry/Info；config/normalize.ts 真的解码 lsp 键；session-summary.spec.ts 把 "LSP" 当服务分区在测（含 toHaveCount(0) 的状态点断言）；file-mutation.ts / edit.ts / write.ts 各留一条 "after LSP runtime exists"；doc/ 七节里没有 LSP。
  • 对方机制：powernap 默认目录 + Manager.Start(path) 按被触碰文件惰性启动 + skipAutoStartCommands 拒绝清单；notifyLSPs 后把 getDiagnostics() 追加进 edit/write 的工具结果；7 个模型工具；header 错误徽标。
  • 顺序即成本：M-a 只做诊断回灌并终结死配置；M-b 只上两个工具（表面预算归 L18/L30，别在这一 PR 重开）；M-c 可长期搁置。
  • 两条禁止：失败必须可见（对方是 slog.Error + 删 client + "continuing anyway"）；首步延迟不得上升 —— 用 script/session-efficiency.ts 同 prompt/同模型前后各跑一次。
轴：验证 / 能力面 / 进程证据：本轮实测（本仓）+ 摘要实测（对方）

CR-7 邻接没有局部守卫 先做 · 0.25d

不是断言有 bug，是把"不会发生"从推理变成断言。

  • 我方实测：to-llm-message.ts 的 toolResult() 只对 completed 与 error 有分支，调用处 return result ? [call, result] : [call]，另一条管子还带 .filter(m => m !== undefined) —— 历史里若存在 streaming/running 态调用，请求里就会出现没有 result 的 tool call。
  • 现有兜底：runner/llm.ts 的 settleStaleToolCalls（drain 起点，发 Tool.Failed + type: "aborted"）、step.ts 的 failUnsettledTools + failIncompleteTools、history.ts 的 preview 只取 settled 前缀。
  • 为什么值得记：对方注释里同样的形状被描述为"strict-adjacency providers (e.g. Kimi, DeepSeek) … permanently locking the session"。我们有三道防线但没有局部断言。
轴：循环证据：本轮实测（本仓读码，未构造出该状态）

CR-8 台账过时 先做 · 0.25d

对照时撞出来的 doc-sync 债务：缺口早被填掉，台账还当它是 P1。

  • 我方实测：runner/loop.ts 的 decide() 有四类判据（repetition() 的 WINDOW=25 / MAX_PERIOD=5 / REPEAT_LIMIT=5、declinedRun() 的 8、REJECT_LIMIT=3、MALFORMED_LIMIT=3），落地在 08aef689be；doc/session-loop.md 已有专节与 session-runner-loop.test.ts。
  • 过时处：优势对比清单.md §3.2 的"命中为 0"、§4 缺口表的"无通用重复/空转断路器"、§六 复核命令的"空 = 无通用断路器"。今天该 grep 命中 5 条。

口径与限制

  • 收益分不是实测。它是 1–5 分的工程判断；本页唯一的实测数据是工期估算与证据等级。
  • CR-1 的端到端未证。本轮实测的是 classify() 与 save 两层；「批准一次 → 第二次是否真不问」必须在真机跑一次（清单第七节第 1 条）。若那一跑被别处拦住，CR-1b 撤下、CR-1a 缩到只修 git -c *。
  • CR-5 与 CR-6 的收益栏是假设。对方机制存在，但我方现状没测：内联工具输出的 ANSI 走向、每帧成本是否随列表长度增长。两项都记「先量」，不许直接开工。
  • 对方的循环内核不可见。fantasy 未 vendor，本轮读不到工具并发上限、邻接处理与 finish 判定；本页不提供任何"谁的 loop 更强"的结论。CR-9 是这条边界的收口动作。
  • 三处对方结论仍挂在子代理级别。GrantKey 的精确形状、skipAutoStartCommands 的 28 项内容、hasRepeatedToolCalls 的输出哈希触发条件 —— 动手前逐行复核 crush-借鉴清单.md §五.4。
  • 工期是工程日，不含 review 往返与共识讨论。CR-3a 的 2 天不含"诊断体积上限"的预算决策；CR-3c 的 4 天不含每语言服务器安装的长期维护；CR-1b 的 0.75 天不含"批准过 docker rm 是否等于批准过强删"的产品判断。
  • 依赖会改变实际顺序。CR-2 必须先解掉靠 ruleset 文本反推档位的老路；CR-3b 依赖 CR-3a；CR-3c 撞 L15（Windows 进程树）；CR-3a 的诊断体积接 L29 的预算纯函数；CR-4 的脱敏复用 L37。ROI 排序不等于开工顺序。
  • 所有结论对应基线 51201b6445（2.2.0-fork.11）与 crush 7f418090。任一侧变化后，先重跑清单第六节的复核命令（含那个 9 条命令的 save 探针）。
  • 本页与 16 项 L 账、OpenHands 账共用同一评分模型与四套预设，分数可横比；但本轮增量集中在权限与验证面，在"速度优先"预设下天然吃亏 —— 这正是把 CR-1a 与 CR-8 标为不受预设影响的原因。
