## 3. 逐项施工卡

### 3.1 L30 · MCP schema 字节确定化

**结论（`本轮实测`）**
- `packages/core/src/tool/mcp.ts` 在 `editor.add` 处把 `tool.inputSchema ?? {type:"object",properties:{}}` 直接交给 `input`，无键序处理。
- 数组维度的确定性已由 `Tool.snapshot` 解决：`tool.ts` 里 `definitions` 按名字排序（`sort(([left],[right]) => ...)`）。
- 因此缺口精确落在**单个 schema 内部的键序**与 `required` / `dependentRequired` 的数组顺序。

**前置**：无。这是最便宜的"自证真伪"项：测试写出来就决定 C22 成立与否。

**改动面**

| 文件 | 动作 |
| --- | --- |
| `packages/core/src/tool/schema-canonical.ts`（新） | 纯函数 `canonicalizeSchema` |
| `packages/core/src/tool/mcp.ts` | `editor.add` 的 `input` 先过 `canonicalizeSchema`；`output` 暂不处理（不进 prompt） |
| `packages/core/test/mcp-schema-canonical.test.ts`（新） | 字节恒等 + 幂等 + 不修改入参 |
| `packages/core/test/mcp.test.ts` | 两个语义等价、键序不同的 server schema 产出相同的工具定义 JSON |

**实现规格**

```ts
// 只做字节确定，不做语义折叠（语义折叠是 L18）
export const canonicalizeSchema = (schema: JsonSchema.JsonSchema): JsonSchema.JsonSchema
```

- 递归处理对象键：`properties`、`$defs`、`definitions`、`patternProperties`、`dependentSchemas`、`items`/`prefixItems`、`anyOf`/`oneOf`/`allOf`、`additionalProperties`。
- 数组排序：`required`、`dependentRequired` 的每个值数组；`dependentRequired` 的键本身随对象键排序。
- **不排序**：`enum`、`oneOf`/`anyOf` 分支顺序（保持语义与展示），数组型 `items` 顺序。
- 已规范时返回原对象（引用相等），避免打断 `Tool.snapshot` 的 identity 缓存。
- 输入为空对象或非对象时原样返回。

**测试**

| 用例 | 断言 |
| --- | --- |
| 乱序键 ×2 | `JSON.stringify(canonicalize(a)) === JSON.stringify(canonicalize(b))` |
| `required: ["b","a"]` | 输出为 `["a","b"]` |
| 嵌套 `$defs` / `oneOf` | 递归排序，分支顺序不变 |
| 已规范输入 | 返回同一引用 |
| 两次调用 | 幂等 |
| 集成：MCP schema 键序变化 | 两次 `Tool.snapshot` 的 `definitions` JSON 相同 |

**文档**：`doc/context-economics.md` 新节 "Schema 字节确定" + `Decisions` 一条（C21 数组序 vs C22 内部键序的分工；为什么不做语义折叠）。

**验收**：`cd packages/core && bun test test/mcp-schema-canonical.test.ts`；`bun typecheck`；根 `bun run lint`。

**撤项条件**：若字节恒等测试在未改代码时已通过（说明 snapshot 排序实际覆盖了内部键序），C22 作废，不保留这个纯函数。

### 3.2 L17 · prompt cache 确定性纪律

**结论（`本轮实测`）**
- `session/model-request.ts` 无 `Date.now` / `toISOString`。
- `runner/llm.ts` 保留 `// Keep tool definitions on the final Step to preserve the provider's cached prefix.`，且 `MAX_STEPS_PROMPT` 收尾步不改工具集合。
- 本项**不是"我方完全没做"**，而是把"前缀字节一致"从注释升格为可测断言，并核掉剩余可疑源。

**前置**：L30（schema 字节先稳）。

**改动面**

| 文件 | 动作 |
| --- | --- |
| `packages/core/src/instructions/index.ts` | 把私有 `canonical` 导出为 `canonicalJson`（唯一实现，供前缀哈希复用） |
| `packages/core/src/session/prompt-prefix.ts`（新） | `prefixHash(request, upto?)` 与 `samePrefix(a, b)` |
| `packages/core/test/prompt-cache-prefix.test.ts`（新） | 真实两步请求 + 人为时间注入负例 |
| `packages/ai/src/cache-policy.ts` | 只读核对：`BREAKPOINT_CAP`、`AUTO` 是否含按时间/随机分支 |

**实现规格**

- 前缀定义：同一 drain 内，第 N 步请求与第 N+1 步请求的共享头 = `{ system, tools, messages: 第 N 步的 messages }`。断言：
  ```
  hash({system: reqN.system, tools: reqN.tools, messages: reqN.messages})
  ===
  hash({system: reqN1.system, tools: reqN1.tools, messages: reqN1.messages.slice(0, reqN.messages.length)})
  ```
- `hash` 用 `Instructions.hash(canonicalJson(value))`（SHA-256）。
- `samePrefix` 供 L25 复用：ping 必须与主请求的 `promptCacheKey` 和前缀字节一致。
- 核对项（发现即记录，不静默改）：
  1. `boundImages` 的裁剪点是否只在阈值变化时移动（注释已声明，测试锁定）。
  2. `gatewayPolicy` 分支是否影响 system/tools 的顺序。
  3. per-request 的媒体绑定是否引入请求间差异。

**测试**

| 用例 | 断言 |
| --- | --- |
| 同 turn 两步（普通工具调用） | 共享头哈希相等 |
| 同 turn 三步（含一次拒绝） | 共享头哈希相等 |
| 负例：测试插件在 system 注入 `new Date().toISOString()` | 断言必须失败（证明抓得住） |
| L4 开启路由但集合不变 | 共享头哈希相等 |

**文档**：`doc/context-economics.md` 的 `Decisions`：把"同一 turn 内两次请求前缀字节必须一致"写成纪律，并说明它是 L4/L25/L34 的共同守门人。

**验收**：`cd packages/core && bun test test/prompt-cache-prefix.test.ts`。W1 出口：断言要么跑出脏源，要么证明没有；不允许"加了断言但从未在真实请求上跑"。

### 3.3 L14 · 空响应重试

**结论（`本轮实测`）**
- `runner/step.ts` 在未知 finish reason 时构造 `InvalidProviderOutputError({ classification: "incomplete-stream" })`；`isInterruptedStream` 只认这一类与 Transport read。
- `grep "empty response" packages/core/src/session` 为零命中 ⇒ 缺口真实（C13 settled）。

**前置**：无。与 L1 同改 step 边界，但可独立合入。

**改动面**

| 文件 | 动作 |
| --- | --- |
| `packages/core/src/session/runner/empty.ts`（新） | 常量、token、`decide(messages)` 纯折叠 |
| `packages/core/src/session/runner/step.ts` | `StepRecord` 增加 `toolSucceeded`；`Outcome.Completed` 增加 `empty` |
| `packages/core/src/session/runner/publish-llm-event.ts` | 在工具成功结算时记录 `toolSucceeded` |
| `packages/core/src/session/runner/llm.ts` | `Completed` 分支先判空响应，再判 todo nudge |
| `packages/core/test/session-runner.test.ts` | 三种组合 + 重试上限 + 重启不丢计数 |

**实现规格**

```ts
const MAX_EMPTY_RESPONSE_RETRIES = 3

const EMPTY_RESPONSE_RETRY =
  "Your previous response was empty. Continue the task: call a tool or write the answer the user needs. Do not reply with only an acknowledgement."

const EMPTY_RESPONSE_STOPPED =
  "The model returned an empty response three times in a row, so automatic continuation stopped. Ask the user how to proceed."

const NOTICE_EMPTY_RETRY = "empty-response-retry"
const NOTICE_EMPTY_STOPPED = "empty-response-stopped"
```

- **命中条件**（两条同时成立）：
  1. 本步无任何可见输出：`record.outputStarted === false` 且该 assistant 无 text/tool part。
  2. 本步之前（同一 turn 内）没有成功的 tool response：`record.toolSucceeded === false`，且上一条 assistant 的 tool parts 中没有 `status: "completed"`。
- turn 边界沿用 `SessionRunnerUnfinished` 的 `currentTurn` 规则：最后一个 `type: "idle"` 之后的消息。
- 计数从历史折叠：turn 内 `metadata.notice === "empty-response-retry"` 的 synthetic 条数。超过 3 → 发布 `EMPTY_RESPONSE_STOPPED`（`metadata.notice`），返回 false（idle，**不是 session error**）。
- **与 unfinished 互斥**：本边界若产生空响应结论（retry 或 stop），不再调用 `SessionRunnerUnfinished.decide`——同一 turn 内只允许一个东西在说话。

### 3.6 L1 · 循环失控防护

**结论（`本轮实测`）**

**改动面**

**实现规格**

```ts
// 键：持久化 input 的规范 JSON → SHA-256 前 12 hex
type CallFact = {
  tool: string            // effectiveName
  key: string             // sha256(canonicalJson({ tool, input })).slice(0, 12)
  digest: string          // 结果摘要，见下
  status: "completed" | "error"
  errorType?: string      // 例如 "permission.rejected" / "tool.input-json"
}

type Fold = {
  facts: ReadonlyArray<CallFact>          // 本 turn 内按序
  rejections: number                      // 本 turn 内被 Loop guard 拒绝的次数
  malformed: number
}
```

- **结果摘要**：`completed` 取该 tool part 的 `content` 做规范 JSON 后 SHA-256 前 12 hex——text 原样，file/media 只取 `{ mime, uri }`（不哈希字节）；`error` 取 `error.type + "\0" + error.message`；provider-executed 无本地输出时退化为状态字符串。**必须用持久化副本**（`SessionMessage.Info`），否则重启后同一次调用算出不同的键。摘要提到的"按 `util/src/token.ts` 字符算术哈希"不成立：该模块只有 `estimate`/`estimateWide`，不是哈希。
- **重复判定**：窗口 25；对 `k ∈ 1..5`，若最近 `R*k = 5*k` 条 fact 以周期 `k` 重复且每个周期内 `key + digest` 全等，则触发。`k=1` 即连击 5 次；`k=2` 即 `A B` 交替 5 轮；`k=5` 用满窗口。
- **触发后的反应**：
  1. 下一次同键调用在 `step.ts` 的 `executeTool` 包装被拒：`new Tool.Error({ message: LOOP_GUARD(N) })`。
  2. 拒绝次数从历史折叠（按失败消息 token 计数）；达到 `LOOP_REJECT_LIMIT = 3` 后收束：`llm.ts` 追加 `Message.assistant(LOOP_GUARD_STOP)`，`toolChoice: "none"`，走一次纯文本步后 idle。
  3. **不新增 `DrainResult` 变体**；收束不是 session error。
- **四类计数器**

| 类别 | 计数源 | 上限 | 处理 |
| --- | --- | --- | --- |
| ① 同键重复 | `facts` 的 `key+digest` | `R = 5`，`LOOP_REJECT_LIMIT = 3` | 拒绝下一次同键 |
| ② 无副作用步 | 现有 `unfinished.ts` | `STALL_LIMIT = 3` / `MAX_NUDGES = 10` | 不重复实现，L1 只读它的结论 |
| ③ 连续权限拒绝 | `errorType === "permission.rejected"` 的同键 | `DECLINE_LIMIT = 8` | 收束，文案用 `POLICY_DENIED` 语义 |
| ④ 畸形产出 | `tool.input-json` / `tool.input-incomplete` | `MALFORMED_LIMIT = 3`（写进文案） | 收束，提示语含上限数字 |

- **前进定义**：出现未见过的键，或同键但 `digest` 变了。重复的 `edit`（同键同结果）不算前进——这正是 `unfinished.ts` 的"真实副作用"判据在这里不够用的原因。
- **开关**：`experimental.loop_guard`（布尔，默认 `true`，前提是 `poll-is-not-a-loop` 同一 PR 合并）。关时折叠直接返回 `none`，零行为变化。

**契约 token（字面保留）**

```
Loop guard: this exact tool call (same arguments, same result) has been made N times in
a row. Repeating it will not help. Change the arguments to get new information, use a
different approach, or ask the user.
```

```
Loop guard: automatic continuation stopped after repeated identical tool calls. Change the approach or ask the user before continuing.
```

**测试**（`packages/core/test/session-runner-loop.test.ts`，用 `session-runner.test.ts` 的 `TestLLM`/`compileRequest`；时间用 `TestClock`，不 `sleep`）

| 用例 | 断言 |
| --- | --- |
| 同参同结果 5 次 | 第 6 次被拒，消息含 `Loop guard` |
| 改参数 | 重置，不拒 |
| 不同工具交替 | 不触发 |
| `A B A B` 交替 | 打断（连击判据做不到，这是净增益） |
| 同参不同结果的轮询 | **不打断**（C4 配重） |
| 连续 8 次权限拒绝 | 收束；文案是 `POLICY_DENIED` 不是"空转" |
| 畸形输入第 3 次 | 收束；提示含 `3` |
| 重启（新 runner、同 DB） | 四类计数都不归零 |
| 收束后的状态 | idle，不是 session error |
| 开关关闭 | 零行为变化 |

**文档**：`doc/session-loop.md` 的 "Stopping, continuing, and nudging" 表加三行；`Decisions` 记四件事：durable fold 而非内存 Map；结果参与键且三家原文都漏；四类计数器分病因共享收束；上限必须对用户可见。`CHANGELOG.md` 记默认开启那一刻。

**验收**：`cd packages/core && bun test test/session-runner-loop.test.ts`；默认开启前用 §5 的测量协议跑一次对比。

**决策点**

- 收尾步的拒绝文案：现有 `"Tools are disabled after the maximum agent steps"` 对 loop guard 不成立，改为 `"Tools are disabled for this closing step."`，两处共用。

### 3.15 L26a · formatter 静默失败必须可见（本轮就做）

**结论（`本轮实测`）**
- `formatter.ts` 把子进程 `stdin/stdout/stderr` 全设 `"ignore"`；异常走 `Effect.logError` 后 `Effect.as(undefined)`；非零退出只日志并 `return false`。
- `edit.ts` 拿到 false 后直接回读原文，模型收到的 diff 里没有任何"格式化失败"痕迹；`write.ts`、`patch.ts` 同型。

**前置**：无。这是已核实的静默数据丢失，无论 L26b 共识如何都该修。

**改动面**

| 文件 | 动作 |
| --- | --- |
| `packages/core/src/formatter.ts` | `file` 返回结构化结果；stderr 改为 `"pipe"` 并截尾 2 KB |
| `packages/core/src/tool/plugin/edit.ts` | 失败时在工具结果里追加模型可见说明 |
| `packages/core/src/tool/plugin/write.ts` / `patch.ts` | 同上 |
| `packages/core/test/formatter.test.ts` | 失败可见、成功无噪声、截断有界 |

**实现规格**

```ts
type Result =
  | { ok: true }
  | { ok: false; reason: "disabled" | "failed"; command?: string[]; exitCode?: number; stderr?: string }

file: (filepath: string) => Effect.Effect<Result>
```

- 失败说明（模型可见）：
  ```
  Formatter failed: <command> (exit <code>)
  <stderr tail>
  The file was written without formatting. Fix the formatter or the file contents.
  ```
- stderr 只保留尾部 2 KB，避免把整段构建日志灌进 prompt。
- `reason: "disabled"` 不产生提示（用户主动关闭）。
- 不新增 `execute.after` 钩子；结果直接进工具输出，模型下一轮自然看到。

**L26b 的门槛（不写码）**：只有共识题（摘要 §6.9）的结论为"验证属于循环"时，才用 `tool.hook("execute.after")` + Synthetic 注入验证结果，并复用 L1 的计数器骨架（按病因分文案）；否则 L26 以 L26a 收束。

**文档**：`doc/session-loop.md` 一段；`Decisions` 记"formatter 失败不再静默"。

**验收**：`cd packages/core && bun test test/formatter.test.ts`。
