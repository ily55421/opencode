## 2. 一句话结论（按复核后改写）

**我们没有在「单次执行不出事」这条轴上领先**：codex 有 OS 沙箱栈 + 决策代数 + 空转断路器，kimi 有 AST 危险命令策略 +
三级重复断路器，ZCode 有 pre-push 受影响测试 + 租约/陈旧拒绝。**我们确实领先的是「长期演进不出错」这条轴**：
事务内投影 + 日志可选、单源契约与三口味 codegen、作用域的类型层约束、以及唯一会被 CI 跑的文档锚点校验。

因此行动方向不变：**借清单里的 P0/P1（决策代数、prompt-as-data、工具表面预算、run generation）仍是真缺口**，
而 §3 列出的领先项**不构成**回退它们的理由。

## 3. 逐条优势对照（复核后仍成立的部分）

### 3.1 权限：升级不被「记住的批准」消音——**优势真实存在，但比上次说的窄**

| | 机制 | 同一层的漏洞 |
| --- | --- | --- |
| **我们**（实测） | `packages/core/src/permission.ts` 的注释：`An escalation outranks every allow rule, a saved "always allow" included`；`tool/plugin/shell.ts` 在解析产出为空且不安全时用 `fallback` 补 resource；`shell/danger.ts` 的 `BANNED_SAVE`（`xargs`、`sudo`、`doas`、`env`、`nohup`、`command`、`busybox`、`pwsh`、`powershell`、`cmd`、`python`、`perl`、`ruby`、`php`、`node`、`bun`、`deno`、`osascript`）清空 `save` 列表 | 折叠仍是 `findLast` + 顺序即语义，通配 allow 可表达；没有 `Decision` 那种带 `Ord` 的代数 |
| **codex**（对方实测） | `execpolicy/src/decision.rs` 的 `Decision { Allow, Prompt, PromptUser, Forbidden }` 带 `Ord`，`policy.rs` 用 `matched_rules.iter().map(...).max()` 折叠成**最严者胜**；`rule.rs` 的 `PrefixPattern.first` 按首 token 精确取桶、**通配符不可表达**；`codex-rs/core/src/exec_policy.rs` 的 `BANNED_PREFIX_SUGGESTIONS` 让解释器类命令不产生「永久允许」建议 | **同层漏洞已确认**：`policy.rs` 里危险启发式包在 `if matched_rules.is_empty() && let Some(heuristics_fallback)` 内——任何一条命中的 allow 会让危险检查完全不参与决策。这一半不要抄 |
| **kimi**（对方实测） | `dangerous-command-ask.ts` 的 AST 策略 + `unanalyzable` 类别，`git-control-path-access-ask.ts`、`sensitive-file-access-ask.ts`、`features/tower/bashGuard.ts` 同族 | `features/externalHooks/internal/runHook.ts` 在 spawn 失败、流错误、超时、abort 四条路径**全部 `allowResult`**，文档 `docs/en/customization/hooks.md` 自认「This "allow on failure" design is called fail-open」 |

**净结论**：我们唯一的、别人都没有的性质是「**危险升级发生在规则匹配之后**」。codex 的代数在结构上更硬，但它的危险判定是
「无规则命中时的兜底」，等于把一个 allow 变成免死金牌；kimi 的策略最细，但它的钩子层是 fail-open。
→ 这条值得写进 `doc/permissions.md` 的 `Decisions`，并在改动时守死。

### 3.2 循环可靠性：**我们不再领先，改口径为「我们的实现方式更耐重启」**

- 我们（实测）：`runner/unfinished.ts` 的 `decide(messages)` 从 **durable 历史** fold 出 `turn.nudges`/`turn.stalled`，
  `MAX_NUDGES 10` / `STALL_LIMIT 3` / `ESCALATE_AFTER 3`，notice token `todo-residue` / `todo-residue-stopped`；
  `doc/records/2026-10-todo-completion-nudge.md` 记录了为什么否决进程内 `Map<SessionID, number>`。
- kimi（对方实测）：**两种都有**，且性质不同——`agent/toolDedupe/toolDedupeService.ts` 的重复断路器阈值
  `REPEAT_REMINDER_1_START = 3 / _2 = 5 / _3 = 8 / REPEAT_FORCE_STOP_STREAK = 12`，状态存 `AgentStateService` 的内存 `Map`
  且那些 key **没有** `.replayable(...)`，所以进程/Agent 重建即归零；而 `features/todo/todoListReminder.ts` 的
  `TODO_LIST_REMINDER_STEPS_SINCE_WRITE = 5` 是 `getTodoListReminderStepCounts(input.history)` **从历史扫描**得来，跨重启存活。
  另有 `agent/interruptionReminder/interruptionReminderService.ts` 的「上次被用户中断，上面的部分输出是不完整的」与
  `agent/tools/agent/subagent-task.ts` 的 `[partial output]` 标记。
- codex（对方实测）：`codex-rs/ext/goal/src/accounting.rs` 的两个 3-turn 阈值 + `continuation.md` 的完成度审计 +
  `codex-rs/ext/goal/src/spec.rs` 把「同一阻塞条件连续三个 goal turn 才允许 blocked」写进**工具 schema**。
- **我们的缺口**：`grep -rn 'repetition|loopDetect|isLoop|stuck' packages/core/src` 命中为 **0**（实测）。
  即：**我们没有任何通用重复/空转断路器**，只有 todo 残留这一种。kimi 有 3/5/8/12 四级，codex 有 3-turn 空转。

→ 正确说法是：「我们的续跑判据活在 durable 层，重启不会把有界重试变成无界花费；但判据种类比两家少。」

### 3.5 分发：从「领先」改为「广度领先，签名能力对齐」

- 我们（实测）：**12** 个 Bun 单文件目标（含 linux musl × 3、non-AVX2 baseline × 3）、发布通道
  `npm / cli / desktop / docker / homebrew / aur / winget / github-release`、`sign-macos`、`sign-windows`、
  `publish-attestations`（Sigstore）。
- kimi（对方实测）：6 个原生目标 + `.sha256`、macOS 公证（`.github/actions/macos-notarize`）、
  Windows **Azure Trusted Signing**、安装面 `npm/pnpm/yarn/bun-global + homebrew + native + install.sh`。
  → 签名不是我们的独有能力。我们的差异在**架构广度**（musl / baseline / docker / AUR / winget）与**证明链**（attestations）。
- codex（对方实测）：**不收外部贡献**（`docs/contributing.md`："We do not accept external code contributions or pull requests."），
  CI 有 `blob-size-policy`、`cargo-deny`、`codespell`、`bazel`；无覆盖率闸门、无 mutation、无 SBOM、无 PR-size 机器限制。
- 我方 `bunfig.toml` 的 `exact = true` + `minimumReleaseAge = 259200`（只装发布满 3 天的版本）与 codex 的 `cargo-deny`
  是同一类供应链闸，**形态不同，不宣称领先**。

## 4. 不是优势：对手确实更强或我们缺失（复核后更准）

| 缺口 | 我们的现状 | 对手已实现的具体形状 | 借鉴清单位置 |
| --- | --- | --- | --- |
| **无 OS 沙箱与网络出口策略** | `SECURITY.md` 的 `No Sandbox`：权限系统「是 UX 特性，不是安全隔离」 | codex：四套沙箱栈 + `network_rule(host, protocol, decision)` 与命令规则同一 DSL，`host` 明确**不允许通配符**，编译成 `(allowed, denied)` 出口名单 | 沙箱本体**不学**（TS/Bun 重写不现实）；`network_rule` 这一小块可学 |
| **权限不是决策代数** | `findLast` + 兜底 `ask`；通配 allow 可表达 | codex 的 `Decision` `Ord` + `.max()` 最严者胜；`PromptUser` 语义是「需要一次全新的人为决定，独立于所配置的审查者」，且 `try_derive_execpolicy_amendment_for_prompt_rules` **只为 `Prompt` 生成写回**，`PromptUser` 不生成 | P0 |
| **无通用重复/空转断路器** | core 内 `repetition/loopDetect/stuck` **零命中** | kimi `3/5/8/12` 四级提醒 + 强制终止；codex `consecutive_empty_turns >= 3` + `No-progress check` | **新增，应插到 P1**：这是绝对领先项，且我们只有 todo 一种判据 |
| **prompt 不是数据** | 只有 `InstructionBaseline`（drain 内冻结）与按模型 thinking dialect | codex `WorldState`：`trait WorldStateSection { type Snapshot; render_diff(previous) }`、SHA-1 `WorldStateHash`、RFC 7386 `merge_patch_from`、`Placement::{Prefix, Standalone, Mergeable}`，**未变节不产出文本**；注意 removal notice 不是通用机制，而是**每节自带文案**（`context_window_guidance.rs` 的 `REMOVAL_NOTICE`、`model_catalog.rs`） | P1 |
| **工具表面不计 token 预算** | `snapshot(permissions)` 只按权限过滤，schema 每步全发 | codex `codex-rs/core/src/tools/handlers/tool_search.rs` 的 BM25（`bm25 = "2.3.2"`）+ `ToolExposure::{Direct, Deferred, DeferredModelOnly, DirectModelOnly}` + `defer_loading`，并有 `context/world_state/tools_budget.rs` 的共享字节预算 | P5 |
| **无 run generation / 陈旧写入识别** | claim 键只有 SessionID + 时间戳，`SessionEvent.Execution.Started` payload 只有 `{sessionID}` | ZCode 的真实形状比记忆里说的轻但有效：batch key 含 `runId`，`lease.runId !== command.runId → STALE_TASK_OWNER_COMMAND`，两处拒绝点；`runId` 是 prompt `traceId` 字符串 | P2「run 世代号」——**对方也没用数字世代**，所以我们的实现可以是 opaque id + 比较，成本比预想低 |
| **pre-push 不跑测试** | `.husky/pre-push` 只做 bun 版本断言 + `bun run check`；根 `test` 脚本是 `do not run tests from root` 护栏 | ZCode pre-push = `lint && db:schema:check && test:architecture && architecture:check -- --changed && test:unit:affected --scope push` | P7 |
| **无全图依赖方向检查** | 五个边界测试（均为 upstream 所写），`core ↛ protocol` / `protocol → 仅 schema` / `tui ↛ core` 靠约定，`tui` 那处泄漏因无测试而活着 | ZCode `architecture-policy.yaml` 888 行 / **82** 个模块（45 个 `managed: true`）+ `forbidCycles` + `layerOrder` + `forbidDeepImports` + `maxFileLines: 800` + `maxPublicMethods: 12` + 五件套产物规则（`module.ts`/`contract.ts`/`contract.example.ts`/`contract.test.ts`/`CONTRACT.md`） | P0-1；**做法是扩展现有五个测试**，且可借它的 `unmanaged-new-file`（拒绝未登记新文件）这一条便宜闸门 |
| **无覆盖率/mutation/SBOM/PR-size** | 实测均缺失；`.github/workflows` 里 `coverage\|mutat\|sbom` 只命中 `check-process-daemon.yml` | codex 也没有（对方实测），但它有 `blob-size-policy` + `cargo-deny` + `codespell`；ZCode 有 `max-lines` 规则与 19 文件豁免清单 | 三家都没有 → 不是相对劣势；`blob-size` 与 `codespell` 是便宜可借项 |

## 5. 该守的三项 + 该补的三项

**守（都是本轮实测确认的唯一性）**

1. **升级优先于任何 allow**（`escalation outranks every allow rule, a saved "always allow" included`）。
   这是三家在**同一层**都留了洞的性质：codex 的危险判定是「无规则命中才跑」，kimi 的钩子是 fail-open。
   守住的最便宜办法：给「每个工具都声明 `options.permission`」加一条断言测试——目前没有 schema 保证它。
2. **会被 CI 跑的文档锚点校验**。三家都在这一点上失败：codex 的 docs 近 300 提交零改动且无链接校验，
   kimi 的 `AGENTS.md` 与 `scopes.ts` 直接矛盾且一致性脚本已死，ZCode 有 spec-first 约定但无锚点校验。
3. **durable 层的续跑判据 + 双轨压缩**（`mechanism: "trigger" / "endpoint"` 与后台预压缩）。
   kimi 的重复断路器不跨重启，我们没有对应物；这条组合是差异所在。

**补（按复核后的成本重估）**

1. **通用重复/空转断路器**——新发现的真缺口，且三家已证明可行；我们缺的是它而不是 todo nudge。
2. **run generation 用 opaque id 而非世代号**——ZCode 的实现比原以为的便宜，`STALE_TASK_OWNER_COMMAND` 那对比较就是全部。
3. **pre-push 跑受影响测试**——`turbo.json` 的 `transit` 已经把「依赖变更重查依赖者」做在 typecheck 上，测试面照搬即可；
   抄 ZCode 时必须连它的事故注释一起抄：`unset $(git rev-parse --local-env-vars)`，
   原文注释是「Git hook 会注入 GIT_DIR/GIT_WORK_TREE 等 local env。不清理会让单测里的临时仓库 Git 命令误命中当前仓库（例如把功能分支改名为 main）」。
