评分模型

工程判断，不是实测

与 16 项那页同口径：单个维度 1–5 分，加权后 ×20 映射到 100 分；唯一的实测数据是工期估算与证据等级。 这样做的理由是这批收益大多不是"功能有没有"，而是"装错版本时少背多少锅、失败时用户能不能自救"。 切换预设，象限、ROI、热力表总分、对比表全部重算。

OH-1 桌面版本纪律 先做 · 1.0d

本轮唯一的 P0：重连场景直接采纳任意在跑的后台版本，而且没有文档。

  • 对方机制：config/defaults.json 单一真源 + check-sdk-version-sync.mjs 拒绝任何版本 range + 启动期 assertAgentServerVersionIsSupported 三种稳定错误码；版本解析失败当失败，不当通过。
  • 我方实测：cli-version.ts 的 serviceVersion 在 mode === "reconnect" 时 return undefined；版本不符替换只有 logInfo；doc/ 无桌面版本这一节。
  • 成本：构建期守卫近免费（opencode-cli.version 已在 extraResources filter 里）。
  • 边界：fork 版本永远不等于上游，校验必须是下限/区间，不许照抄对方"pin == 下限"的耦合。
轴：交付证据：本轮实测（双方）

OH-0 title 成本不落账 先做 · 0.25d

不是借鉴项，是对照时照出来的本仓缺陷：钱被记成 durable 事件，然后哪张报表都不去读。

  • 实测：UsageRecorded.source 是 ["title","compaction"]；title.ts 确实按 "title" 发布；但 stats.ts 里唯一读 UsageRecorded 的查询带着 $.source = 'compaction' 过滤。
  • 文档：doc/usage-stats.md 只写了 compaction 会折进 tokens，没有任何一句说明 title 被排除。
  • 对方对照：它按 usage_to_metrics 的任意 key 聚合，condenser 与 profile:<name>:<uuid> 分账一律并入总账。
  • 验收：session-stats.test.ts 已经发布了一条 0.5 USD 的 title 事件，断言里加它的去向即可。
轴：账目证据：本轮实测（本仓）

OH-2 stdio MCP 运行时诊断 先做（前置实测）· 0.75d

事实实测存在，危害未测。不许按这张卡直接开工——先在本机跑一次桌面 + npx MCP。

  • 对方做法：electron/main.mjs 显式把打包的 uv 与 Node 注入 PATH，注释写明"打包后系统 PATH 极小，command: "npx" 会 ENOENT"；dev 模式故意 no-op，找不到时大声 warn 且不动 PATH。
  • 我方实测：extraResources 只带 CLI；preferApplicationEnvironment 在 win32 把 shell 置 null，不探登录环境。
  • 不抄的半截：打包 Node（体积 + 与 Bun 单文件 CLI 职责重叠）。抄诊断：把"命令找不到"变成有名字的 runtime-missing 分类 + 可操作文案。
  • 未确认：Windows 由 Explorer 合并 HKCU\Environment，所以"npx 一定找不到"不成立；真正丢的是 shell profile 追加的条目。
轴：交付证据：待验证

OH-3 反向工具（UI 交给模型） 战略 · 3.0d

本轮唯一让能力面变宽的一项，也是唯一需要先动协议与权限档位的一项。

  • 对方机制：ClientToolSpec 带 readOnly/destructive/idempotent/openWorld annotations 随启动载荷下发；claim-client-tool-call.ts 用 localStorage 记账挡住重放重复执行，账本损坏时不阻塞调用；secret-request.ts 回传只有 {status,name,guidance}，永不含值。
  • 我方半条腿：TUI 已有 client-hosted MCP（ClientMcp）；GUI 插件契约 Browser.open、Command/Panel/Slot 存在但没有桥成模型可见工具；notifications/coordinator.ts 的 claim 已是比对方更强的幂等基线。
  • 必须一次带三件：annotations（决定权限档）、幂等 claim、结果回灌走合成 inbox 控制项。
  • 反面：它没有结果通道，只能把结果当 user 消息回灌、再靠文本前缀从聊天里隐藏（注释自承 brittle by design）。我们的幂等 ID 规则从结构上消掉了这个妥协。
轴：能力面证据：摘要实测（现状半边未复核）

OH-6 + OH-7 交付纪律 0.75d / 2.0d

两条都是"让约束可以被机器检查"，共同点是先复用本仓已有形态，不新造框架。

  • OH-6 机制：对方用守卫测试（递归遍历 src、相对路径 allowlist 而非散落的 disable、显式处理 Windows 路径分隔符）并自写 AST 规则展开 TemplateLiteral 求静态 URL，补上正则抓不到的绕过。
  • OH-6 落点：本仓 agents.md 写了 Schema → Core/Protocol → Server 的分层方向，但无机械强制（ZCode 轮已自我更正过一次）；形态照 script/doc-refs.ts 套。
  • OH-7 机制：对方 test-mapping.json 做 源码 glob → e2e 子目录；约 43 个"工具链自身"测试，含 Dockerfile 漏 COPY 即失败；CI 脚本本身也跑测试。
  • OH-7 落点：我们只有包粒度 turbo --affected。优先给 script/pack.ts 与 tag-release.sh 加自测——它们重写全 workspace 版本号，出错静默。

OH-5 + OH-11 穷举守卫 0.5d + 0.5d

同一件事的两个面：新主题/新键不能"静默继承"或"静默缺译"。都刚好处在合适的时间窗。

  • 对方机制：src/themes/README.md 声明三套渲染系统（CSS/HeroUI、Prism+Monaco、xterm）必须同时被覆盖，映射表写成穷举 Record，理由写得很直白："新主题不能悄悄继承深色"。
  • OH-5 时机：Indigo 主题与 rail 主题切换刚落地（3558c4c / 82efecf），是加守卫成本最低的时候。
  • OH-11 实测：本仓 packages/ui/src/i18n 约 60 个语种文件，但 no.ts 用穷举 Record<Keys,string>，bs.ts/de.ts 用 satisfies Partial<...> —— 后者缺键静默回退。
  • 只借机制不借规模：它 2207 键 × 16 语种的全量翻译不是我们要的东西；我们要的是"生成键枚举 + 拒绝把英文原样复制进各语种"。
轴：主题 / i18n证据：本轮实测（对方 README + 我方 i18n）

OH-4 事件组进度摘要 规划 · 0.75d

纯体验项，成本低，但要先复核我方现状（子代理报告，不可直接采信）。

  • 对方机制：event-group.tsx 把同一个组当"活尾"时主位显示当前动作、副位显示 "k/n actions completed"；一旦被后面的条目超过，计数升为主位并带成功勾。带推理的事件会先冲刷当前组、单列成一项，保证推理不被折进折叠组里消失。
  • 另一件好事：deriveLiveActivity(events) 是纯函数，反向遍历解出唯一未回答的动作，role="status" 渲染，不需要后端支持。
  • 我方现状（待复核）：TUI 已有分组与 "3 commands, 1 edit, 2 reads" 分类计数，但没有 k/n；GUI 只有 todo-pill 有 N/M。
  • 硬约束：只动组内摘要行，状态行的 tok/s、缓存命中、上下文百分比必须原样保留。
轴：体验证据：摘要实测

OH-8 mutation 的入门姿势 条件 · 0.5d

这条的真正价值是更正一条既有撤下理由，不是马上开工。

  • 对账更正：既有轮次以"覆盖率、mutation、SBOM、PR-size 门三家都没有"撤下 mutation。本轮事实推翻该理由：OpenHands 有，而且是无阈值的低成本形态。结论可以保留，理由必须改写。
  • 它的姿势：stryker.config.mjs 只 mutate: src/**、开 vitest.related、完全不设阈值，文档明说"report-only，先建立基线"；diff 模式用 --incremental --force --mutate <files>；进程边界用 // Stryker disable all。
  • 若做：只跑 session/stats.ts 这类纯折叠代码，不接 CI。我们已有 fast-check 属性测试与语料防自欺守卫，mutation 的边际收益取决于前两者抓不到的那类变异。
轴：测试证据：本轮实测（对方配置）

口径与限制

  • 收益分不是实测。它是 1–5 分的工程判断；本页唯一的实测数据是工期估算与证据等级。
  • OH-2 与 OH-10 的收益栏是假设。事实存在（我方实测），危害未测：前者要先跑一次桌面 + npx MCP，后者要先在真实窗口复现拖拽是否被吃掉。
  • 三处现状结论仍挂在子代理级别。OH-3 的 ClientMcp 只暴露两个工具、OH-4 的 activity-summary 是否有 k/n、OH-9 的 MCP 状态机分类 —— 动手前必须逐行复核，清单第六节已列出。
  • 对方的后端层不在本页范围内。agent 循环、压缩算法、成本计算、模型目录都在 Python 仓，本仓不可见；任何"它的 loop 更好/更差"的说法都没有依据，本页不提供。
  • 工期是工程日，不含 review 往返与返工。OH-3 的 3 天不含权限档位的共识讨论；OH-7 的 2 天不含映射表的长期维护。
  • 依赖会改变实际顺序。OH-2 与 OH-9 同批；OH-3 等 M1/M3 的档位结论，且其提示词注入部分撞 L17/L34 的字节稳定纪律；OH-6 复用 script/doc-refs.ts 的形态。ROI 排序不等于开工顺序。
  • 所有结论对应基线 81738639df 与 80ddd49ef。任一侧代码变化后，先重跑 OpenHands-借鉴清单.md 第八节的复核命令。
  • 本页与 16 项那页共用同一评分模型与预设权重，所以两页的分数可以横比；但本页项目多为交付与工程纪律，在"速度优先"预设下天然吃亏，这正是把 OH-1/OH-0 标为不受预设影响的原因。
